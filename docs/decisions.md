# 關鍵決策紀錄

記錄「為什麼這樣做」，以及當時考慮過但否決的選項。目的是讓半年後的自己不會把已經踩過的坑再踩一次。

---

## D1：資料源用 yfinance，不申請付費 API

**決定**：行情、基本面、股利、歷史價、年度 EPS、匯率全部走 `yfinance`（非官方 Yahoo Finance 介面）。

**否決的選項**：Finnhub / Tiingo / Polygon.io（要申請 key、免費額度有限）。

**理由**：自用工具，免費且零設定。匯率也吃得到（`USDTWD=X`），不必再接第二個服務。

**代價（已實際踩到）**：非官方介面會暫時失敗。建構過程中曾遇到 NVDA 基本面回傳空值，導致畫面顯示「無可用模型」——與「這檔無法估值」無法區分。因此加了 retry 與 `資料不足` 狀態（見 D5）。

**何時該換**：若失敗率變高、或要即時報價。換掉只需改 `market.py`，其餘模組不動。

---

## D2：成本基礎用移動平均法，不用 FIFO

**決定**：每次買進累加成本、賣出按當時均價釋放成本並結算已實現損益。

**理由**：使用者要的是「我的平均成本」用來判斷加碼，不是報稅數字。

**代價**：與券商報稅用的 FIFO / 指定稅務批次**不同**，數字會有差異。工具內已標註「不是報稅依據」。

---

## D3：估值模型加適用性閘門，而非全部取中位數

**決定**：每個模型判斷自己是否適用，不適用的排除在中位數計算外。

**當時的錯誤版本**：四個模型直接取 median。結果 AAPL 被 Graham（$37.91）與 DDM（$22.46）拖成「低估 68%」——那是模型誤用產生的假訊號，不是分析結果。

**理由**：一個不適用的模型不是「另一個觀點」，是雜訊。

**額外設計**：只剩單一模型適用時（成長股常見），輸出明確警告「結論等同於你的假設，脆弱度高」。

---

## D4：歷史 P/E 有穩定性閘門

**決定**：用該檔近 5 年每日收盤價 ÷ 當時**已公布**的年度稀釋 EPS 算出 P/E 分布取中位數；但四分位距 > 中位數 × 0.8 時拒用。

**理由**：NVDA 的歷史 P/E 中位數 73.9，四分位距 46–134。EPS 4 年成長 28 倍讓 trailing P/E 完全失真，那個 73.9 沒有預測意義。給出來比不給更糟。

**已知限制**：yfinance 只提供 4 個會計年度的年度 EPS，所以是年度顆粒度而非逐季；且用 trailing EPS，對高成長股系統性偏高——這正是 NVDA 被拒用的原因。

**快取 30 天**：年度 EPS 一年只變幾次。

---

## D5：區分「行情抓取失敗」與「無法估值」

**決定**：`Fundamentals.is_empty`（所有欄位皆 None = 抓取失敗）→ 基準標示 `資料不足`；資料到齊但無可用模型 → `無`。並在 `fundamentals()` 加一次 retry（丟棄快取的 Ticker 後重抓）。

**理由**：見 D1 的代價。使用者看到「無」會以為這檔不能估，實際上只是暫時抓不到。

---

## D6：台幣換算存每筆交易的成交日匯率

**決定**：`transactions` 表加 `fx_rate` 欄位，匯入時自動回填；匯率快取在 `fx_rates` 表。

**否決的選項**：只用今日匯率換算現值（工作量小很多）。

**理由**：用今日匯率換算成本會把匯率損益混進股票損益，算出來的台幣報酬率是錯的。實測真實匯出檔，同一段期間內各筆交易的成交日匯率就有明顯差異（每筆都不同）。

**歸因公式**（兩者精確相加 = 台幣總損益，有測試守著）：
- 股票漲跌 = `(現值美元 − 成本美元) × 今日匯率`
- 匯率變動 = `成本美元 × (今日匯率 − 成本均價匯率)`，其中成本均價匯率 = `台幣成本 / 美元成本`

**絕不用未來匯率**：查不到當天就回溯前一交易日，最多回溯 10 天；找不到就留空不填。用未來匯率會無中生有製造獲利。

---

## D7：認證採 fail-closed

**決定**：未設 `PORTFOLIO_API_TOKEN` 時，`serve` 拒絕綁定非本機位址並說明原因。

**理由**：持倉、成本、帳戶淨值不能裸奔。預設安全比預設方便重要。

**實作**：Bearer header（行動端）或 httpOnly cookie（瀏覽器），`/api/session` 是唯一公開端點供前端判斷是否要跳登入。

---

## D8：`/api` 不可快取，app shell 必須重新驗證

**決定**：`/api/*` 回 `Cache-Control: no-store`；`/` 與 `/index.html` 回 `no-cache`（仍走 304，不是 no-store）。

**當時的 bug**：瀏覽器快取了舊的 `index.html`，而 API 已經回新增的台幣欄位——**新 API + 舊 shell = 版本錯位**，畫面上的函式根本不存在。另一次是一個失敗的行情回應被快取凍結在畫面上。

**理由**：價格與提醒狀態永遠不該來自快取；shell 與 API 必須同步。

---

## D9：網頁前端不用框架

**決定**：單一 HTML 檔，inline CSS + vanilla JS，無 build step、無 npm、無外部 CDN。

**理由**：六個分頁的表格應用，React 只會多出 build tooling。離線可開、單檔好備份、資料不外傳。

**代價**：1,100+ 行在一個檔案裡，沒有元件化，**沒有前端單元測試**（專案沒有前端測試框架、不引入 npm）。渲染邏輯靠 `node --check` 與人工瀏覽器驗證覆蓋。這是對「必寫 UT」規範的已知例外。

---

## D10：行動端用 Expo（React Native），不是 PWA（已由 D25 取代）

**決定**：Android app 用 Expo Go 跑，不打包上架。

**當時的建議是 PWA**，理由是省掉第二套 codebase。但使用者是 Android，不需要 Apple Developer 帳號（$99/年），Expo Go 掃 QR code 就能跑——原本的成本反對意見大幅失效。

**前提**：行動端**必須有雲端後端才看得到資料**。所以順序是「後端上雲 + 認證」先，app 後。

**代價**：兩套 UI 要維護。且 app 是在台幣功能之前建的，目前**不顯示台幣歸因**。

---

## D11：`Settings` 的建構集中在測試工廠

**決定**：`tests/conftest.py` 的 `make_settings()` 是唯一建構 `Settings` 的地方。

**理由**：每加一個設定欄位就打爛三個測試檔，發生兩次之後改掉。

---

## D12：智慧提醒的「AI 判斷層」用確定性樣板，不呼叫 LLM

**決定**：規則觸發後的一句話摘要（`advisor.py`）是**確定性樣板**，只把已觸發的條件連同數字講成人話，結尾一律帶「這只是規則觸發，非投資建議」。

**否決的選項**：真的呼叫一個 LLM 來生成摘要。

**理由**：
1. **原則 1（只給基準、不給建議）**：摘要層若能自由發揮，很容易滑進「建議買入」。樣板從結構上就不可能給建議——它只能描述 `Signal` 裡已經觸發的條件。需求文件自己也寫「AI 不自己發明判斷邏輯，只是把你設定好的規則講清楚」。
2. **離線可測**：全專案測試都離線跑（見 D1 的教訓）。樣板無外部呼叫，輸出可被逐字斷言，也不會因模型更新而漂移。
3. **可擴充**：`SignalNarrator` 是一個 Protocol。未來要接 LLM（需求文件的「第二層」）時，實作同一個介面即可——但契約寫死：narrator 只能描述已觸發的條件，不能新增規則、門檻或買賣判斷。

**代價**：摘要讀起來像模板，不如 LLM 自然。可接受——這一層的價值在「準確複述規則」，不在文采。

---

## D13：技術指標用還原股價，但「均價偏離」用原始報價

**決定**：`signals.py` 的技術指標（RSI、均線、布林）一律吃 `market.close_prices`（`auto_adjust=True` 的**還原股價**）；但「現價 vs 我的均價」這條規則用的是**即時原始報價 vs 你 CSV 匯入的原始成本**。`evaluate_signal` 因此吃一個獨立的即時價（`PositionPricing.last_price`，與均價成對傳入）。

**理由**：需求文件的「除息/分割」陷阱。抓歷史算均線/RSI 若用未還原股價，除息日會被誤判為大跌、狂觸發假訊號——所以指標一定要用還原價。但「我賺賠多少 / 離我的成本多遠」是拿實際會成交的原始價，去比你實際付的原始成本，兩者都不該被歷史還原係數扭曲。混用會讓「偏離均價 X%」這個數字失真。

**額外設計（假訊號 vs 大盤）**：`MarketContext` 另外看基準指數（預設 SPY）近 5 個交易日的走勢。買側訊號遇到大盤同期也大跌時，摘要標注「比較像大盤整體在動」。這對應需求文件的第一個「先想清楚」：規則要能區分個股訊號與大盤系統性下跌。

**同日去重**：沿用到價提醒的邏輯——同檔同日同一組觸發條件只通知一次，條件組合變了自動重新武裝（`signal_alerts` 表存 `last_conditions`）。

---

## D14：回測要同時看「頻率」與「準確度」

**決定**：`backtest.py` 除了報觸發頻率與區間，還算每次**買點進場當日**往後 20/60 個交易日的報酬分布（樣本數、勝率、中位數、平均）。

**理由**：需求文件要的是回測「頻率**與準確度**」。只看頻率只能篩掉「門檻太鬆、天天觸發」的無資訊規則；要判斷規則有沒有預測力，得看觸發後實際發生什麼。只算**episode 起點**（進場事件），一段連續觸發只計一次，否則長期低檔會灌水；用**還原股價**，且**絕不看未來**（`position+h` 超出資料就跳過）。這是規則的事後表現，非保證、非建議。

---

## D15：智慧提醒的行情快取用「每天抓一次」而非「新鮮度天數」

**決定**：`price_history` 存還原收盤，另用 `price_fetch_log` 記每檔「最後抓取日」。同一天內第二次評估直接讀快取；跨天才重抓。抓取失敗時回退舊快取，而不是回空。

**否決的選項**：用「最新一筆價格日期距今幾天」判斷新鮮度。盤中最新可得的收盤是「昨天」，用那個判斷會每個 tick 都判定為過期 → 每 30 分鐘重抓一年資料，等於沒快取。

**理由**：智慧提醒吃日線，一天抓一次就夠；盤中即時價另外從 `client.quote` 拿（給均價偏離用）。這樣多檔輪詢也不會一直打 yfinance（對應需求文件的 API 額度顧慮）。**代價**：指標最多落後約一個交易時段，對「找買點」用途可接受。

---

## D16：LLM 第二層是「可選、依賴注入、預設關」

**決定**：`advisor.LLMNarrator` 吃一個 `complete(system, user)` callable，不直接綁 SDK；Anthropic 後端在 `anthropic_completion()` 裡**惰性 import**，`anthropic` 放在選用的 `llm` extra；`PORTFOLIO_LLM_NARRATION` 預設關；任何錯誤（缺套件、缺 Key、網路）都回退確定性樣板。

**理由**：延續 D1（自用、免費、零設定、測試離線）與 D12（摘要層不得發明判斷）。依賴注入讓它離線可測（餵 stub `complete`）；惰性 import 讓基礎套件不因此變重；強制附免責 + 只餵事實的系統提示，讓即使模型亂講也不會變成買賣建議。Key 只從環境變數讀，不進 repo（需求文件的 API-key 安全點）。

**已知落差**：網頁與手機分頁已接，但 UI 未經視覺驗證（本機無 Android 模擬器）。

---

## D17：`signals set` 的 CLI 指令函式保留 5 個參數，不收攏成值物件

**決定**：`cli.py` 的 `signals_set` 維持 `symbol` + 四個 `float | None` 共 5 個參數，違反「參數 ≤ 4 個」的專案規範。四個門檻值一進函式就立刻包成 `ThresholdOverride` 交給 `_save_threshold(override)`，所以真正帶著邏輯走的只有一個值物件。

**否決的選項**：讓 `signals_set` 直接吃一個 `ThresholdOverride`。typer 是用函式簽名反推 CLI 介面的——一個函式參數對應一個旗標。參數換成 dataclass 後，`--rsi-oversold` 這類旗標會全部消失，typer 會試著把它當成單一位置參數解析，指令直接壞掉。

**理由**：這是框架邊界，不是設計失誤。既有的 `assume_set` 也是同一個形狀。把「宣告 CLI 介面」與「處理門檻覆寫」切開：指令函式只負責宣告旗標並組裝值物件（危險的連續 `float | None` 只存在這一層，且每個都被 typer 的旗標名字綁死，叫錯順序不可能發生）；`_save_threshold` 以後只看得到值物件。

**代價**：新增一個門檻欄位要同時改 `signals_set` 的簽名與 `ThresholdOverride`，兩處會短暫不同步。檢查腳本也會永久回報這一處違規——它就是這條決策記錄存在的原因。

## D18：「今天已通知」以實際送達為前提，而非以規則觸發為前提

**決定**：`run_signal_check` 只在 `options.notify and any_delivered(deliveries)` 為真時才寫入同日抑制狀態與觸發歷史。

**否決的選項**：維持原本的無條件 `_record_signals_fired(settings, fresh)`。這讓「標記為今天已發送」與「實際上有沒有送出去」脫鉤，實際造成兩個缺陷：(1) 使用者設定 Telegram 之前，桌面通知在 Linux 上是關的、Telegram 是空的，`dispatch_signals` 沒有任何管道可送，訊號卻仍被標記，於是當天永久被抑制——30 分鐘輪詢在最需要重試的時候不重試；(2) `--no-notify` 的 dry-run 會污染真實狀態，吃掉當天的通知。2026-09-17 實際發生：MSFT 與 VTI 當天觸發卻不會送達，且歷史留下兩筆從未送出的假紀錄。

**理由**：抑制的目的是「不要重複騷擾」，前提是**已經騷擾過一次**。沒送達就不成立。這也讓 `signals history` 的自我說明（「過去實際觸發並通知過」）名實相符。

**代價**：完全不設通知管道、只用 CLI/網頁看的使用者，`signals history` 會保持空的。可接受——門檻調校靠 `signals backtest` 的歷史價格重播，不依賴這張表。另外 `--resend` 仍會為同一天寫入第二筆歷史，這是刻意的：那確實是第二次通知。

**連帶**：三個既有測試與 `test_api.py::test_signal_check_records_history` 都是照著錯誤行為寫的（用 `notify=False` 或零管道設定卻斷言狀態被寫入）。改成用 stub 管道提供真實送達，而不是把行為改回去。CLI 輸出同步把三種狀態分開：未發送（`--no-notify`）/ 已送達 / 沒送出去會重試——原本 `--no-notify` 顯示「無可用通知管道」是誤導。

---

## D19：門檻校準必須跟「隨機進場基線」比，而不是看絕對勝率

**決定**：以 5 年日線回測校準三檔的智慧提醒門檻，判準是「訊號後的報酬**優於同期無條件進場**」，而不是勝率高低。結果：MSFT 乖離 20 / RSI 20-80；NVDA 乖離 25 / RSI 20-80；VTI 乖離 15 / RSI 20-80。

**理由**：過去 5 年是大多頭，絕對勝率會系統性好看。無條件基線（同一檔任一天進場、持有 20/60 交易日）：

| 標的 | 20d 基線勝率 / 中位 | 預設門檻訊號 | 校準後訊號 |
|---|---|---|---|
| MSFT | 52.9% / +0.7% | 54.3% / +1.8%（觸發 28.1%） | **57.9% / +3.0%（觸發 11.4%）** |
| NVDA | 62.1% / +3.1% | 64.1% / +5.6%（觸發 53.5%） | **75.0% / +7.7%（觸發 19.8%）** |
| VTI | 63.1% / +1.7% | 60.5% / +2.5%（觸發 19.7%） | 60.0% / +2.5%（觸發 12.4%） |

**VTI 的結論是負面的**：不論怎麼調門檻，勝率都**低於**無條件基線。全市場 ETF 的「等跌再買」在這個區間輸給「隨時買」。因此 VTI 的門檻只調到「降低雜訊」的程度，不聲稱它有預測力——它的觸發應當被視為現況描述，不是進場依據。

**已知落差**：
1. 樣本僅 28–46 段，勝率 ±8–10pp 在雜訊內。單一 5 年多頭區間，無法外推到空頭。
2. 回測**不評估賣方訊號**的後續報酬（`ForwardReturnStats` 只量測 BUY 進場點），所以 RSI 超買與突破上軌的門檻沒有實證支撐，只是對稱地跟著調。
3. 回測**不套用均價條件**。`backtest_signals` 的 `average_cost` 參數若填入今天的均價，等於拿未來資訊回推 5 年前的價格：實測 NVDA 的 `BELOW_AVERAGE_COST` 會在 85.9% 的日子成立（今天的持倉均價在 2021–2025 幾乎永遠高於當時股價），把觸發率從 53.5% 灌水到 88.9%，並讓門檻調校看起來完全無效。CLI 因此刻意不傳這個參數。**真實引擎用它是合理的**（今天的價格對今天的成本），只有回測不能。

## D20：每日淨值快照用 systemd timer，不塞進 app 的背景迴圈

**決定**：雲端以獨立的 `stockcapy-snapshot.timer`（`OnCalendar=Mon..Fri 21:30 UTC`、`Persistent=true`）每個交易日跑一次 `stockcapy snapshot`，不放進 `periodic_alert_check`。

**否決的選項**：加進既有的 30 分鐘迴圈。那個迴圈是 sleep-first 設計（避免每次重啟都爆一串通知），用來做「每天一次」的工作需要自己記日期、且重啟會漂移。systemd timer 的 `Persistent=true` 直接處理「開機時已錯過執行時間就補跑」，零程式碼。

**理由**：快照資料**不可追溯**——今天沒存，今天的淨值就永遠沒有了（券商不提供歷史淨值）。這類任務要的是「保證每天一次、錯過會補」，正是 timer 的語意。21:30 UTC 在美股夏令（20:00 UTC）與冬令（21:00 UTC）收盤後都成立。

**代價 / 已知缺陷**：`stockcapy snapshot` 的 `--cash-balance` 預設 0.0，寫入是 `INSERT OR REPLACE`。自動化後，使用者手動填的現金餘額會在當晚被 timer 蓋回 0。這是自動化把既有的潛在問題變成系統性問題，待修（`--cash-balance` 應改為 `float | None`，省略時保留該日已存的值）。

## D21：行情資料過期就不發訊號，並且要說出來

**決定**：`_signal_for_symbol` 在收盤序列的最後日期超過 `MAX_SIGNAL_DATA_AGE_DAYS = 5` 天時回傳 None，不產生訊號；過期的標的改由 `detect_stale_signal_data()` 單獨回報，進入 `SignalCheckOutcome.stale`，CLI 與 `/api/signals/check` 都會顯示。

**理由**：2026-10-13 在正式環境發現，MSFT 在 09-27、09-28、09-29、10-07、10-08 五天送出「突破布林上軌」通知，記錄的價格全是 **$497.75**——那是 **9 月 18 日**的價格，當天實際收盤分別是 529.76 與 522.61。根因是兩層靜默回退疊加：`_signal_pricing` 取不到即時報價時回退到 `snapshot.last_close`，而 `_fetch_adjusted_closes` 下載失敗時回退到舊快取。兩者都「合理」，疊起來就變成拿三週前的資料計算布林通道，再把三週前的價格當成現價送到手機。

**關鍵認知**：即時報價正常**救不了**這件事。所有指標（布林、RSI、均線）都來自收盤序列，報價只影響「低於均價」這一條。收盤序列舊了，觸發條件本身就是在描述過去的某一週。所以閘門擋的是訊號本身，不是只換個價格顯示。

**否決的選項**：只在訊息上標註資料日期。上游那兩個 commit 已經加了「指標資料截至 X」這行，但實測證明不夠——使用者收到的仍是一則看起來正常的買賣訊號，日期只是一行小字。錯的訊號不該因為附了日期就可以發。

**沒有沉默**：過期時若只是不發訊號，「行情壞掉」和「市場平靜」在畫面上完全一樣（都是空清單）。因此 `stale` 一定要單獨回報。

**代價**：連線不穩時會有一段時間完全沒有訊號。這是刻意的取捨——沒有訊號比錯的訊號好，而且現在看得見。

**已知落差**：抓取為什麼會間歇性失敗還沒查明（疑似 yfinance 對 e2-micro 共用 IP 限流），已列入 progress.md。

## D22：刪除 2026-09-17 那筆淨值快照（口徑變更）

**決定**：移除 `account_snapshots` / `position_snapshots` 中 2026-09-17 的資料（已先備份 DB）。

**理由**：那筆快照存於「股利證實的股數納入持倉」之前，匯出區間之前買進的那批股數尚未計入，記錄值因此明顯偏低；隔天同一個投資組合的淨值大幅跳升。淨值走勢因此顯示「一夜暴漲數十個百分點」，整條曲線的百分比全部以這個錯誤基準計算，累積報酬被灌大到遠高於真實報酬。

這不是市場波動，是資料模型改變。同一條序列裡混兩種口徑，等於讓圖表說謊。

**否決的選項**：用修正後的口徑回填那一天。做得到（持倉與當天收盤都查得到），但那會變成「事後製造一筆從未真實記錄過的快照」，與這張表「每天實際記錄一次」的語意衝突。少一天比多一天假資料好。

**教訓**：資料模型變更會污染既有的時間序列。往後若再改變持倉的計算口徑，必須同時決定歷史快照怎麼處理。

## D23：行情快取的閘門看「內容」，不看「何時抓過」

**決定**：`_fetch_adjusted_closes` 改為在「快取已含最近一個應發布的收盤日」時才直接回傳；否則就重抓。判斷由 `market_calendar.is_close_series_current()` 負責，不再參考 `price_fetch_log`。

**理由**：舊閘門問「今天抓過了嗎」。VM 跑 UTC，排程的第一個 tick 落在 00:00 UTC 之後 ＝ 美東 20:00，距收盤僅 4 小時，yfinance 當日的日線往往還沒發布。抓到的是前一天為止的資料，`fetched_on` 卻被標記成今天，於是整整 24 小時不再嘗試。接著只要遇上一段抓取失敗，序列就會卡住更久——2026-10-13 實測時快取停在 10-09，而手動清掉標記重抓，10-12 的 541.15 立刻就進來了。資料一直都在，是閘門不讓它進來。

這和 D18（通知）、D21（訊號）是**同一個錯誤模式**：把「嘗試過」當成「成功了」。三個地方都用一個狀態同時代表兩件事，而它們會分岔。

**發布緩衝**：`US_CLOSE_HOUR_UTC = 21`（取冬令時間，全年都安全）加 `PUBLISH_BUFFER_HOURS = 3`，所以要過了 UTC 午夜才會期待當天的日線。這讓「還沒發布」不會被誤判成「資料壞了」。

**否決的選項**：保留日標記但改存時間戳、限制每小時重試一次。需要改 schema，而且仍然是以「嘗試」為中心——錯的那個軸。

**代價**：市場假日時本模組不知道休市，會多期待一天，於是整天每個 tick 都重試（每檔每天至多 48 次，四檔約 192 次）。相對於原本每天 4 次是增加了，但對 yfinance 仍屬溫和；而且這個方向是安全的——多一次請求只花一個 request，少一次會讓所有指標悄悄凍結。

**連帶效果**：正常日子反而**更少**抓取。舊版每天固定抓一次；新版在快取已經是最新時完全不連網。

**已知落差**：為什麼抓取會間歇性失敗（疑似 yfinance 對 e2-micro 共用 IP 限流）仍未查明。這次修的是「失敗之後不會自我修復」，不是「不會失敗」。

## D24：iPhone 用 PWA 外殼，不另外做 iOS app

## D26：持續觸發的智慧提醒，靠「再走 N%」或「滿 N 天」才重發

## D30：成長股補 PEG 與 DCF，合理價附不確定性並浮動安全邊際

**決定**（2026-11-06）：估值模型從四個擴充為六個，新增 **PEG（成長調整）** 與 **DCF（現金流折現）**，各自帶適用性閘門（延續 D3）；每個合理價附**不確定性等級**，安全邊際在不確定時**加寬**，但使用者明確設定過就不動；智慧提醒改用與完整視圖相同的假設解析，並在合理價下方揭露採計模型、不確定性、實際邊際與倍數來源。

**起因**：一則 NVDA 提醒顯示合理價 $129.24、入手價 $103.39，現價 $181.60。追查後不是 NVDA 特例：高本益比 + 不配息會把 Graham 與 DDM 都排除，只剩 Target P/E，合理價 = EPS × 18，再打八折。而提醒路徑為了輕量**固定用預設倍數**、又丟掉模型數，所以看起來很篤定，其實只靠一個假設。

**做法與理由**
- **PEG**：合理前瞻 P/E = PEG 目標(1.0) × 成長%，成長取「預估 EPS ÷ 實際 EPS − 1」並以 20% 封頂（成長不會永遠維持）；< 15% 不採計（低成長時「倍數 = 成長」會算出 2 倍之類的荒謬倍數）。配前瞻 EPS，所以成長不會算兩次（D3 / `valuation.py` 註解指出的陷阱）。
- **DCF**：10 年成長逐年線性淡出到終值成長 3%，以使用者的要求報酬率折現。金融業（現金流是放款）與不動產（折舊低估現金流）不採計。未加淨現金、未扣股票薪酬，註明於模型說明。
- **不確定性**：單一模型 2 點、模型分歧 ≥ 75% 1 點、盈餘劇變（預估 vs 實際 EPS 差 ≥ 40%）1 點 → 低/中/高/極高 → 邊際下限 0/30/40/50%。單一模型權重較高，因為它與「分歧」互斥（分歧需要兩個模型），等權重會讓最高級永遠到不了。
- **只加寬不收窄；使用者設的邊際照用**：延續「假設是使用者的判斷」。`AssumptionOverride.apply_to` 只要帶 `margin_of_safety` 就把 `adaptive_margin` 設為 False，不需要新欄位也不改 schema。
- **提醒與完整視圖一致**：提醒改走 `resolve_assumptions`。原本刻意不做是怕提醒週期多抓五年歷史；歷史 P/E 有 30 天快取，只有第一次要抓，失敗就退回預設＋覆寫，不會丟掉提醒。

**否決／暫不做的選項**
- **同業中位數當倍數**：yfinance 沒有穩定的同業清單 API；逐檔抓同業基本面又重又脆，且在沒有網路的環境無法驗證，寧可不做。
- **Justified P/E**（(1−g/ROE)/(r−g)）：穩定成長率取 4%、要求報酬率 9% 時，ROE 30%～100% 的公司算出來是 17～19 倍（ROE 15% 也只有 14.7 倍），與預設 18 倍幾乎重疊，只會讓模型數虛增而沒有獨立資訊。
- **PEG 目標取 1.5～2**：1.0 是 Lynch 的公平線，是文獻上最常引用的值；要更寬鬆，用 Target P/E 的倍數選項（15／20／25 預設）去表達。
- **把安全邊際收窄成使用者以下**：違反「假設是使用者的」。

**代價與已知限制**
- DCF 對自由現金流與成長假設極敏感：它與每股自由現金流嚴格成正比（用假設輸入掃過，FCF 從 4 到 8，DCF 從 97 變 195），終值佔比大。它是三個模型之一而不是唯一，中位數會壓住單一極端值，但仍應當作粗略參考。
- 預估 EPS 來自賣方共識（yfinance `forwardEps`），不是工具自己的預測。
- 所有成長相關參數（PEG 目標 1.0、成長上限 20%、終值成長 3%）目前是程式內預設值，沒有逐檔持久化。
